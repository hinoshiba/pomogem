# 実機ジェム監査（v1.2 の瓶と宝石）

状態: 下記の範囲だけ完了です。2026-09-29、`main`（12dc663）の Release ビルドを iPhone 12 mini に上書きで入れ、
待機中の Home、起動、手動で積んだ粒の着地、GPU、メモリを測りました。12dc663 には、v1.2 の宝石の絵・適応倍率・
止まった瓶の省電力（#47）、完走カードと融合シート（#52）、結晶カード（#57）と、監査セッションの修正が入っています。

- **止まった瓶の省電力は実機で保たれています。** 描画ループの停止（jar-01）と Core Motion の間引き（dev-D2）の効果は、
  12dc663 でも 5601527 と同じ水準でした。待機中の Home 30秒で、CPU 0.8%、起床は約1回/秒、ヒッチは0です
  （3246ab6 は4.1%、約123回/秒）。
- **着地で、宝石の描画はメインスレッドをほとんど使っていません。**
  - 宝石の絵とアトラスは2〜4 ms、メインスレッドの SpriteKit は 5601527 と同じ量でした。
  - 落下から着地までのメインスレッドの山（210 ms の窓）は121・118 ms で、5601527 の126 ms と同じ水準です。
  - 着地の前後で増えたメインスレッドの大半は、HomeView の再計算です。今回は「iCloudを確認中」の表示で測ったので、
    確認中の合計の計算が加わっています。
- **今回の作業による退行が3つあります。**
  1. 起動時に、ガラス v2 の3枚のテクスチャをメインスレッドで2回描いています。これが、Home を作り始めてから
     瓶の最初のフレームまでのメインスレッドの42〜72%を占めます（#47）。
  2. 3246ab6 と比べてメモリが約30 MiB 増えたままです。GPU 側で v1.2 由来と分かる分は、ガラス14.1 MiB と
     宝石のアトラスなど約7.8 MiB です。4 GB の端末で問題になる量ではありません（#47）。
  3. 結晶カードの置き場所の計算（`aggregateCardPlacement`）が、Home を描き直すたびに `activeSubjects` を
     もう一度計算しています。着地1回あたりメインスレッドで約20 ms です（#57。小さい）。
- **GPU の1フレームは、目安の予算を超えています。** 中央値は2.0〜3.0 ms で、§7.13 の予算1.2〜1.8 ms を超えます。
  それでも1フレームの16.7 ms には十分収まっていて、コマ落ちの原因にはなっていません。

Simulator の値、unit test、UI test を実機の確認の代わりにはしません。設計と予算は
[GemExperienceDesign.md](GemExperienceDesign.md) の §7.13 を正本とします。

## 目的

v1.2 で瓶と宝石の描画は大きく変わりました。3Dローポリの宝石、瓶全体の適応倍率、ガラス v2、ジェムベッド、時間の核、
瓶の舞台の光、止まった瓶の省電力です。§7.13 の予算と省電力の効果は、これまで Simulator の代わりの指標でしか
確かめていませんでした。予算の前提である A14（iPhone 12 mini）の実機で、次の5点を確かめることが目的です。

1. 待機中の Home の電力です。次の2つの直りが、#52・#57 の後も保たれているかを確かめます。
   - jar-01: 止まった瓶でも、SKView の表示リンクが毎秒60回メインスレッドを起こしていた。
   - dev-D2: 落ち着いた瓶でも、傾きを毎秒30回メインスレッドで受けていた。
2. 起動から瓶の最初のフレームまでの時間と、その間にメインスレッドで何が動くか。
3. 粒の着地のヒッチと、メインスレッドの山。
4. 宝石の面の描画、縁のシェーダ（`JarLightEdgeFade`）、ガラスの GPU 負荷。
5. メモリの使い道（アトラス、核、ベッド、舞台の光）と、4 GB 端末で気にする量かどうか。

## 方法

比べる値（3246ab6・5601527）は、監査セッションが同じ端末で同じ手順を使って取ったものです。今回の値も同じ道具で
解析しました（`analyze-trace.sh`、`profile_summary.py`、`window_profile.py`、`landing_profile.py`）。
比べる値の記録も同じ道具で解析し直し、報告どおりの値になることを確かめてから比べています。

| 計測 | 手順 | 記録の名前 |
| --- | --- | --- |
| 待機中の Home（30秒×2回） | test07 で Home を保持し、Animation Hitches＋Time Profiler＋Activity Monitor を名前で付けます（比べる値と同じ手順）。ハーネスは20秒ごとにステータスバーを叩きます | `idle1`、`idle2` |
| 止まった瓶の GPU（10秒） | 同じ保持の間の Metal System Trace | `mst-idle` |
| 起動から瓶の最初のフレームまで（3回） | App Launch テンプレート。各回の前にアプリを終了させ、バンドル ID で `xctrace --launch` します | `launch1`〜`launch3` |
| 起動後の GPU と Metal のメモリ | 起動からの Metal System Trace（16秒） | `mst-launch` |
| 起動時のメモリの推移 | 起動からの Activity Monitor。XCUITest は付けません | `am-launch` |
| 着地（手動で積む1・2回目） | test11（`MANUAL_ADDS=3`、`PROFILE_PAUSE`）の1回目の前の目印から、Metal System Trace を60秒 | `mst-landing` |
| CPU 側のメモリの内訳 | Allocations／VM Tracker（20秒） | `alloc-home`（下記のとおり書き出せません） |

- 「瓶の最初のフレーム」は、瓶の形を作り終えた後の最初の SpriteKit の描画です。
- 起動の CPU 時間は、スレッドの状態が「実行中」の区間から数えました。App Launch のサンプルの重みは待ち時間を
  含むので、CPU 時間には使っていません。
- 着地は2つの相に分けて比べました。
  - 手動で積んだ粒は、保存の確定（`HomeView.commitPendingManualEntry`）の直後に瓶の口から落ち始めます。
    5601527 では、確定の1.4秒後に着地の触覚が鳴っています。
  - そこで、確定の前0.3秒〜後0.5秒を「落下の始まり」、後0.5秒〜2.5秒を「落下から着地まで」とします。
  - それぞれの相で、メインスレッドの時間がいちばん多い210 ms の窓を探しました。比べる値と同じく、
    Time Profiler のサンプルで数えています。
  - XCUITest が画面を読み取る時間（AXRuntime）はハーネスの都合なので、それを除いた値も並べます。

## 読み方

### 待機中の Home の電力（jar-01、dev-D2）

**jar-01 の直りは保たれています。** 次の3点から、止まった瓶はフレームを作っていません。

- 待機30秒のメインスレッドの SpriteKit は2〜3 ms です。3246ab6 では81 ms、表示リンクを含むメインスレッドの全体は
  1,073 ms でした。
- 起床は約1回/秒です。3246ab6 では約123回/秒でした。
- 止まった瓶の10秒の Metal System Trace には、PomoGem のコマンドバッファが1本もありません。

**dev-D2 の直りも保たれています。**

- Core Motion のスレッドは30秒あたり22〜24 ms（毎秒5回の待機の傾きのフィルタ）で、メインスレッドの受け手は0 ms です。
- 3246ab6 ではモーションのスレッド113 ms＋メインの受け手21 ms、5601527 では32 ms＋4 ms でした。

待機中にいちばん大きいのは、瓶ではなく `ScreenTimeIntegrationModifier.refresh` です。

- 約3.07秒ごとに6〜12 ms 動き、30秒あたり84〜106 ms になります。
- 内訳は `ScreenTimeStore.withState` 60〜72 ms、`ScreenTimeController.reload` 33〜41 ms などです。
- 3246ab6 から同じ水準で、v1.2 で増えたものではありません（監査セッションの持ち分）。
- スクリーンタイムを設定していない端末でのこの更新は、監査セッションの #58（未マージ、P6）が止めます。

Potential Interaction Delay（35〜47 ms）は、ハーネスが20秒ごとにステータスバーを叩いたときに出ます。
3246ab6 でも同じ形で出ています。

### 起動から瓶の最初のフレームまで

- 最初に描かれるのは、瓶ではなく iCloud の起動画面です。0.88／0.52／0.51 秒に出ます。
- その後、iCloud の確認の門が 3.78〜4.36 秒まで Home を待たせます。その間、メインスレッドはほとんど待っています。
- Home を作り始めてから瓶の最初のフレームまでは0.60〜0.88 秒で、メインスレッドはその78〜96%の時間動いています。
  - そのうち `JarScene.glassTextures(for:neckInset:)` が42／72／69%（包含）を占めます。
  - ほかは `JarAmbientStage.body` 11〜20%、`JarStageArtwork.image` 7〜15%、SoundSynth と触覚の準備が約2%です。
- 1回目だけは、システムのフレームワークの初期化が冷えていました（220 ms。2・3回目は26 ms）。

ガラスは Core Graphics で、メインスレッドで**2回**描かれています（`HomeView` の `@State private var scene = JarScene()`）。

- 1回目は、`JarScene.init` の最後の `rebuildGeometry()` です。既定の大きさ（`defaultSceneWidth`×`Jar.height`）で描きます。
- 2回目は、SKView の実際の大きさで来る `didChangeSize` の `rebuildGeometry()` です。
- キャッシュの鍵は大きさなので、2回目は当たりません。1回目の3枚は画面に出ないまま捨てられます。

宝石の絵は起動を止めていません。

- 起動時の先焼き（別スレッドの `GemArtwork.drawGem`）は、瓶の最初のフレームの0.5〜0.8 秒前に終わります。
  粒は最初のフレームから仕上がりの絵で出ます。
- 最初のフレームの後は、どれも別スレッドで動きます。
  - ベッドのテクスチャ: +20〜64 ms
  - 核の絵（`renderHero`）: +70〜85 ms
  - アトラスのまとめ直し: +0〜180 ms
- メインスレッドでの焼き込みは `bakeMissing` の3 ms だけでした。

起動の後、瓶は6.2〜7.4 秒のあいだ60 fps で起きています。その間、メインスレッドは14.5〜16.4%、別スレッドは
約100 ms/秒です。止まった後のメインスレッドは5〜13 ms/秒に下がります。

### 着地

着地の瞬間のメインスレッドは、次の順に動きます。

1. `HomeView.commitPendingManualEntry` が保存を確定します。
2. 足りない本体をメインスレッドで焼きます（`GemTextureAtlas.bakeMissing` と `GemArtwork.drawGem`、2〜3 ms）。
3. 別スレッドで、ベッドの焼き直し、核の絵、アトラスのまとめ直し（約110 ms）が続きます。

5601527 と比べると、次のとおりです。

- **落下から着地までの山は同じ水準です**（121・118 ms、5601527 は126 ms）。
- **宝石の描画は増えていません。** 確定の前0.5秒〜後3秒で、宝石の絵とアトラスは1 ms に対して4・2 ms、
  メインスレッドの SpriteKit は114 ms に対して122・119 ms でした。
- **落下の始まりの山は大きくなりました。** XCUITest の読み取りを除くと、5601527 の114 ms に対して192・153 ms です。
  同じ3.5秒で、XCUITest を除いたメインスレッドは840 ms に対して1,071・1,017 ms、HomeView・RootView は443 ms に対して
  561・577 ms です。増えた分の中身は次の2つです。
  - 表示の状態の違い: 今回は「iCloudを確認中」の表示で測りました。そのため、確認中の合計の計算
    （`pendingMassHeadline`、`pendingProjectionCoversEverySession`、`pendingMassSessions`）が加わっています。
    着地1回あたり包含でそれぞれ約150・73・36 ms です。5601527 の着地は確定済みの表示で、これらは出てきません。
    どれも 5601527 より前からあるコードです。計測の後に `main` へ入った #56 が、この計算を変えています
    （`pendingProjectionCoversEverySession` と `pendingMassSessions` は無くなりました）。ここの値は 12dc663 のものです。
  - #57: 結晶カードの置き場所の計算（`aggregateCardPlacement(jarHeight:)`）が、Home を描き直すたびに
    `activeSubjects` をもう一度計算します（着地1回あたり21・19 ms）。これは今回の作業による退行です（小さい）。
  - 今回の着地は、比べる値より重い計測器（Metal System Trace）で測りました。同じ条件の比較ではありません。
- 5601527 の33 ms のヒッチに当たる値は、今回は取れていません（「範囲と制限」）。
- **フレームの遅れの原因は宝石ではありません。** 代わりに SpriteKit のフレームの間隔を見ました。
  - 確定から2.5秒の間に、25 ms を超えた間隔が16・20回ありました（うち落下から着地までが12・18回）。
  - その36回の遅れの間にメインスレッドで動いていたのは、HomeView・RootView が606 ms、そのほかの SwiftUI・UIKit が
    267 ms、XCUITest の読み取りが92 ms でした。SpriteKit は22 ms、`JarScene` は1 ms、宝石の絵は0 ms です。
  - 瓶の描画はメインスレッドで行うので、HomeView の再計算が長引くと、そのフレームが遅れます。
  - 着地のたびに Home 全体を描き直す問題は、監査セッションの #58（未マージ、P4）が扱っています。
- 着地のメインスレッドで、音声と触覚のサンプルは0件でした（`landing_profile.py`）。着地の音と触覚が実際に出たかは、
  この記録からは分かりません。

### GPU

- 起動の後に起きている瓶（縁のシェーダ `JarLightEdgeFade`、面のある宝石）: 376本のコマンドバッファを約60本/秒で
  出しています。
  - GPU の区間は中央値2.05 ms、p90 2.56 ms、p99 7.16 ms です。最大15.9 ms は、場面の最初のフレームです。
  - 1フレームの fragment は1.61 ms、vertex は0.35 ms です。
  - 25 ms を超えたフレームは3つで、どれも場面の最初の90 ms の中です。
- 着地の前後: 中央値2.7〜3.0 ms、p90 約5.0 ms、p99 10.3〜11.0 ms、最大11.8〜12.1 ms で、fragment は2.5〜2.7 ms です。
  どのフレームも GPU は16.7 ms を十分に下回ります。
- 負荷はほとんど fragment です。次のものを3倍の画面で重ねる塗りの量が効いていると見ています。
  - 瓶の大きさのガラス3枚（背面と前面は塗り、ハイライトは加算）
  - 縁のシェーダ
  - 大きな宝石
- 粒は1〜3個でもこの値です。§7.13 の「SpriteKit の GPU 1.2〜1.8 ms」は典型の30体を前提にした予算ですが、
  粒が少ないうちからそれを超えています。

### メモリの使い道と、4 GB 端末での見立て

起動の後の Metal のメモリは68.5 MiB でした（1粒）。バックトレースで出どころを分けると、次のとおりです。

| 使い道 | 大きさ | 出どころ |
| --- | --- | --- |
| SKView の描画先 | 25.3 MiB | `CAMetalLayer` の描画先3枚（各6.17 MiB）と、SKView のフレームバッファ6.75 MiB |
| ガラス v2 | 14.1 MiB | 瓶の大きさを3倍で描いた3枚（各4.69 MiB）。2枚は `SKShapeNode` の塗り（背面・前面）、1枚は加算のハイライトのスプライト |
| SwiftUI の画面外の合成（RenderBox） | 16.2 MiB → 9.7 MiB | 全画面1枚9.70 MiB と、起動直後だけの3.97・2.14・0.34 MiB（約10秒後に解放）。どのビューのものかはトレースから分かりません |
| 宝石のアトラス | 6.9 MiB | いちばん大きい `SKTexture` です。瓶の最初のフレームの約90 ms 後に載ります。約1344×1344 px の1ページで、若い瓶の倍率で焼くため大きくなります |
| そのほかのスプライト | 約0.9 MiB | 0.25 MiB が2枚と、64 KiB 以下が7枚。ベッドや光の小物と見られます |
| バッファ | 5.3 MiB | SpriteKit と `SKShapeNode` の頂点、RenderBox のバッファ |

- **アトラス**: GPU 側のページは6.9 MiB でした。Simulator で見込んだ常駐（3倍の画面で約13 MB）は、CPU 側の写しを
  含んだ値です。CPU 側の写しは `GemTextureAtlas.imageByteBudget` の24 MiB が上限ですが、今回の実際の量は確かめられていません。
- **核**: この瓶（1〜4粒）では、まだできていません。核の絵（576 px 四方、約1.3 MiB）は別スレッドで焼かれていますが、
  GPU 側の大きなテクスチャとしては見えませんでした。
- **ジェムベッド**: 小さなテクスチャです（上の「そのほかのスプライト」の中）。
- **舞台の光**（`JarStageArtwork`）: SwiftUI の静止画です。Metal のテクスチャとしては数えられず、CPU 側の画像
  （1.5倍で約1.7 MB）になります。
- **残りの約76〜80 MiB は CPU 側です**（ヒープ、UIImage、フレームワーク）。Allocations／VM Tracker の記録は
  `xctrace export` で表を書き出せなかったので、その内訳は確かめていません。

3246ab6 からの約30 MiB の増加（112〜125 → 151〜156 MiB）のうち、GPU 側で v1.2 由来と言えるのは次の2つです。

- ガラス: 以前は1枚、いまは3枚です。3枚で14.1 MiB、増えた分は約9.4 MiB です。
- アトラスと宝石のスプライト: 約7.8 MiB です。v1.2 より前にはアトラスがありません。

CPU 側の写し（アトラス、ガラスのキャッシュ、舞台の光）も v1.2 で増えているはずです。ただ、3246ab6 の Metal の内訳が
無いので、残りをどこまで v1.2 に帰せるかは確定できません。

**4 GB の端末では問題になりません。**

- 前面のアプリが強制終了される上限は、4 GB の iPhone でおおむね2 GB 前後と広く観測されています
  （Apple は公表していません）。最大の157.6 MiB は、その1割に届きません。
- 粒の数でも増えていません。4粒の起動（XCUITest なし）は、止まった後144.8 MiB でした。1粒の待機（XCUITest あり）は
  151〜156 MiB です。条件が違うので、厳密な比較ではありません。
- 気にするとすれば背景に回ったときです。約145 MiB のまま背景に回ると、メモリが逼迫したときに小さなアプリより先に
  終了されやすくなります。背景での常駐量はまだ測っていません。

直し方の案です（どれもこの PR には含めません）。

2. 結晶カードの置き場所の計算では、`activeSubjects` を本体の中で1回だけ計算して渡すか、空かどうかだけを軽く調べます。

5. GPU の予算は実測に合わせて見直します。ガラスの前面と背面を1枚にまとめる、ハイライトの加算を小さい範囲に絞る、
   などを検討します。そのうえで、典型の30粒で測り直します。

## オーナーの手動確認

遠隔ではできない確認です。どれも、Home に粒が1つ以上ある状態で行ってください。

1. **傾けたときのきらめき**: Home を開いて約3秒待ち、瓶を止めます。
   - 端末をゆっくり左右に傾けると、宝石のグリントとガラスのハイライトが傾きに合わせて動くこと。
   - 傾けるのをやめると、1秒ほどで動きが止まること。
2. **手に持って静止、机に置く**: 手に持ったままじっとしている間も、机に置いた間も、光が揺れ続けないこと
   （センサーのノイズで瓶が起きない）。
3. **揺らす**: 強く振ると瓶が起き、粒が動くこと。0.2秒より短い一瞬のシェイクでは反応が遅れることがありますが、
   これは仕様です（§7.13）。
4. **着地の音と触覚**: 粒が着地したときに音と振動が出ること（消音スイッチを切った状態で）。
5. **メニューの開け閉め**: メニューを開いて閉じた後、瓶が数秒揺れ動いて見えないこと。上の表の #5 を体感で確かめます。
6. **融合**: 次に10粒目を積んだとき、×10の結晶への融合と融合シートが引っかからずに動くこと。
7. **起動**: 起動して「iCloudを確認中」が終わってから瓶が出るまでの間（実測で約0.6〜0.9秒）が気にならないこと。
8. **発熱と電池**: Home を開いたまま10分ほど置き、端末が温かくならないこと。設定の「バッテリー」で PomoGem の
   使用が大きくないこと。
9. **低電力モード**: 低電力モードでは、自発のきらめきと粒子が止まること。
