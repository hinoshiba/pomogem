# 複数端末のiCloud利用 — 安全性と未検証の境界

更新日: 2026-09-12

この文書は開発中の変更を対象とします。審査へ提出した1.0.1 (7)に新しいオフライン動線や
保存先切り替えが含まれているという意味ではありません。

## 通常利用で守ること

同じApple Account・同じデータ世代の端末間では、端末への保存を先に行い、CloudKitへの送受信は
システムに任せます。接続確認の成功を、他端末への反映や全記録の同期完了として表示しません。
Appleの説明でも、ローカル保存・履歴の記録と、システムが予定するexport/importは別の工程です。
([Apple: TN3163](https://developer.apple.com/documentation/technotes/tn3163-understanding-the-synchronization-of-nspersistentcloudkitcontainer))

| 操作・状況 | 実装している処理 | 限界 |
| --- | --- | --- |
| 別々の端末で手動記録を追加 | 異なる記録IDを保持し、それぞれを集計する | 実際の通信で両方向へ到着することは2台の実機で確認が必要 |
| 同じタイマーを引き継ぎ、両端末で完了 | 同じ論理完了IDを重複計上しない。判定に必要な物理履歴は保持する | 分断中に全端末の通知や所有権が一つになるとは保証しない |
| 別々のタイマーを開始・完了 | 異なるタイマーの実測記録は両方保持する | 復旧画面が一つのタイマーを選んでも、別の完了記録を削除する理由にはしない |
| 手動追加の1日上限 | 現在の端末・日付・活動世代のカウンターだけを使う | 過去版が既に自身のカウンターへ取り込んだ他端末分は区別できないため、日付が変わるまで保持する |
| 確認済みの端末でオフライン起動 | 同じ保存ファイルを同期なしで利用し、未送信の記録を保持する | 未確認の初回データを安全なキャッシュとして開かない |
| 通信が回復 | アカウント、保存先の世代、リセット履歴を確認してから同期を再開する | 別のデータ世代と端末変更を自動で結合しない |
| 同じテーマ・成果を同時編集 | 現在のモデルと競合判定で処理する | 同一CloudKit物理レコードへの同時編集が両方保持されることや、操作時刻どおりの最終値は未保証 |

旧データのうち作成端末が不明な手動回数は元の行へ残します。新しい端末の回数として引き継がず、
新たな端末用カウンターから開始します。同期する設定値と、端末だけの利用上限を分離しています。

起動時の確認は、既に別端末で動作中のCloudKit同期処理を止める仕組みではありません。
オフラインの詳細と、同じプロセス内で同期用保存領域を開いた後の制約は
[オフライン利用の設計](OfflineCloudMode.md)を参照してください。

通常起動の通信確認は、アカウント状態・identity・対象controlの取得・identityの順にまとめ、
別途zone一覧を取る確認の重複を減らしました。アカウントとnamespace、controlの2回照合、
記録画面の最終公開前の確認は残しています。通信回数の削減を、古い世代の許可や、複数端末の
排他保証に置き換える変更ではありません。

修正前の通常Hostでは、XCTest本人確認の通過後、HomeとiCloud設定へ進むオンライン試験が1回成功し、
前後の2回は同期用コンテナ作成後の12秒期限切れから再起動案内で停止しました。現在は同条件の
時間切れにオンライン再試行を明示する修正も加えました。修正後は単体1,200件成功・6件skip・失敗0件、
画面16件成功、Release解析成功を確認し、通常Hostの実機オンライン試験も1回成功しました。
続く通信断試験はMacのロックにより条件を設定できず中断しています。通信断用プロファイルは
選択までで開始しておらず、この単一端末の結果を通信断・復帰や実機2台の検証完了とは扱いません。

## コピー途中で別端末の記録が増えた場合

iCloudの取り込みと解除では、ある時点の内容を保存して検証します。その後で別端末の記録が増えると、
再起動後の内容比較が一致せず、同じコピーの再試行だけでは完了できない場合があります。解除時に
端末の未送信記録が残る場合も、元の記録を黙って捨てて一致させることはしません。

これらの非破壊のコピーは、取り込み準備中・保存済みで、最終検証へ進む前だけ取り消してやり直せます。取消しには、元の
保存先が選択されたままで、元ファイルが検証済みコピーと一致すること、同期用コンテナを開いていない
新しいプロセスであることが必要です。元ファイルに追加変更がある場合は削除せず停止します。

取消しの受付を永続化してから未完了処理を解除し、元の記録、iCloudの内容、途中の保存領域と復旧用
コピーをすべて保持します。取消し自体はCloudKitへの通信や保存領域の作成を行いません。再起動後の
通常利用では、引き続きアカウント・保存先の世代を確認します。旧世代への自動復帰は許可しません。

保持したコピーを通常の後処理で削除したり、古さだけで自動削除したりしません。保持受付の上限へ
達した場合も既存のコピーを消さず、新しい処理を止めます。一般向けの復元・結合機能は未実装で、
コピーの保持を即時のUndo機能とは扱いません。iCloud全体の置き換えや最終検証済み以後には、この取消しを
適用しません。

## 全置き換えを通常版で禁止する理由

通常のDebug/Releaseでは、iCloud全体を端末の内容で置き換える操作と、その未完了処理の再開・
別端末からの復旧を禁止しています。画面だけでなく、Runtimeの開始・再開・復旧入口でも、
保存ファイルやCloudKitを変更する前に拒否します。既存の記録、未完了受付、復旧用コピーは保持します。
開始前の取消し、iCloud側を保持する有効化・解除はこの禁止とは別です。

レビューで次の二つの問題が分かりました。

1. 既に起動中の端末や古い版は、置き換え後にも同じ同期zoneへ以前の記録を送信できます。
   現在の同期元モデルには全置き換えの世代を行ごとに隔離する仕組みがなく、検証完了後に届く古い行を
   一律に識別・排除できません。テーマの再出現やリセット世代の食い違いにつながりえます。
2. 二つの端末が同じ未完了処理を復旧すると、一方が削除を認可された後に遅れ、他方が完了した後で
   その削除が実行される順序を排除できません。controlレコードの比較更新は、zone削除まで含む
   一つの不可分な処理にはなりません。テストではこの実行順を代替サーバー上で再現しています。

他端末を閉じる案内、定期的な状態確認、期限付きの実行権だけでは、既に送出された古い処理を無効に
できません。再公開には、遅れた書き込みや削除が新しい世代へ影響できない保存先・実行方式と、
既存クライアントとの互換性を設計する必要があります。世代が異なる端末の未送信記録をどう救済するかも
利用者の明示選択を含めて決める必要があります。

単一端末のDevelopment環境では、全置き換えとアプリ削除後の復旧を実行して一致を確認しました。
これは明示的な試験用許可を使う隔離試験であり、通常版の許可や複数端末の安全性の証拠ではありません。
詳しい範囲は[保存先切り替え](StorageModeTransfer.md)に記録しています。

## 「隔離したDevelopment試験」の訂正（2026-09-20 追記）

本文書とStorageModeTransfer.mdが言う「隔離したDevelopment試験」は、**CloudKitサーバ側だけの
隔離**でした。**端末側の状態は隔離されていません。** CloudKitの環境は署名entitlement
（Debug→Development／Release→Production）で決まる一方、切り替えの受領記録はbundle idだけで
決まるアプリコンテナに置かれていたため、同じbundle idのDebug／Releaseビルドは別々の
データベースを読みながら1つの受領記録を共有していました。

このため、Development環境の監査で得た世代IDを、後から入れたReleaseビルドがProductionへ
突き付ける状態が起こりえます。Production側に転送台帳が無いと比較が成立せず、従来はこれを
「別の端末でiCloudデータが置き換えられました」と表示していました。**端末が1台でも発生し、
置き換えは実際には起きていません。**

- 受領記録に環境とcontainer識別子を持たせ、ファイル名も環境ごとに分けました。環境が確実に
  異なる場合は「置き換え」ではなく「別環境のビルド」として説明します。
- **分離は「見えなくする」ことではありません。** 自分の環境の受領記録が無いときは同じ
  namespaceの他環境のファイルも読み、確実に別環境の記録があれば**停止**します。黙って
  新規登録すると、この端末にある既存のcloudストアを、その台帳を一度も持っていない
  データベースへ同期し始めてしまいます（＝同意付きの「この端末のデータでiCloudを使い始める」と
  同じ結果を、同意なしに起こす）。同じ理由で、新規登録時の「保存領域が空であること」の確認は
  サーバ側の世代の有無にかかわらず常に行います。
- 1つのエラーに潰れていた停止理由を、置き換え／台帳なし／別環境／端末台帳の欠落／端末の
  残存ファイルへ分けました。**どの文面も端末の台数に言及しません。** controlレコードには
  書き込み端末の識別子が無く、自端末が確定させた世代かどうかを判別できないためです。
  内訳は[保存先切り替え](StorageModeTransfer.md)を参照してください。
- サーバに台帳が無いときに限り、この端末のデータで新しい系譜を開始する経路を追加しました。
  置き換えと同じポリシービットの配下にあり、通常版では無効のままです。

## 実機2台で必要な試験

以下は未完了です。単体テストの行投入順を変えた結果を、実際のCloudKit配送の合格へ置き換えません。

| 条件 | 合格時に確認する結果 |
| --- | --- |
| 両端末をオフラインにして別々の手動記録・同名テーマを追加し、順に接続 | 両方のID・記録・重量が残り、名前だけで統合しない。手動回数は端末ごとに保持 |
| 同じタイマーを分断中に引き継ぎ、両端末で完了 | 両方の到着順・再起動後でも論理完了を一度だけ集計 |
| 異なるタイマーを両端末で開始・完了 | 両方の実測記録が残る |
| 完了予定前の中止と保留中の完了を逆順に配送。記録済みの完了後にも中止を配送 | 判定が収束し、既に確定した集中記録を後の中止で消さない |
| 同じ元の物理テーマを一方で削除、他方で編集し、関連する集中記録を遅れて配送 | 削除したテーマが再表示されず、過去の記録と重量は保持 |
| 同じ元の成果レコードを両端末で編集 | 実際の競合結果を確認し、保証できる編集動作を決める |
| 完了履歴と対応する集中記録を別々に受信し、各段階で強制終了・再起動 | 必要な記録が届く前に端末内の復旧情報を捨てず、後から重複計上しない |
| 通信断・低速・再接続を通常画面の操作中に実施 | 待機期限、タイマー継続、端末保存、再起動後の保持、相手端末での内容一致を確認 |
| 古い版・未送信変更のある端末を含む全置き換え | 再設計後の公開条件。現在の通常版では操作を拒否し、元データを保持することを確認 |

実機ではOS版・アプリbuild・保存環境を記録し、接続表示だけでなく、両端末の識別子・内容と
サーバー側の結果を照合します。実データ、アカウント識別子、端末識別子、署名情報は公開文書へ
含めません。Appleの同期調査手順も併用します。
([Apple: TN3164](https://developer.apple.com/documentation/technotes/tn3164-debugging-the-synchronization-of-nspersistentcloudkitcontainer))
